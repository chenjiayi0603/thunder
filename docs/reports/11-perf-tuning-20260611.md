## 四、LuaJIT 加载对性能的误判

> **修正**: 最初 ModuleRaw 64B = 106k (有Lua) vs 207k (无Lua), 差异来自 conf 污染, 非 LuaJIT。

### 排查过程

1. 测出 106k vs 207k → 怀疑 LuaJIT 加载导致降 50%
2. 测「只有 newstate 无 dofile」= 109k → 确认不是脚本编译问题
3. 测 W+X 页: 有 LuaJIT = 0, 无 LuaJIT = 0 → W+X 理论不成立
4. 测 iTLB/cache miss: 有/无 LuaJIT 差异不显著 → TLB 理论不成立
5. 发现 `conf/Hello.json` 在本轮测试中被多次 `python3 -c` 编辑覆盖:
   - module 数从 5 变 2 (lua 模块丢失)
   - `io_backend` 字段被覆盖
   - 配置逻辑不一致导致 Worker 行为不同
6. `git checkout -- conf/Hello.json` 恢复原始配置后:
   - ModuleRaw 64B = **150k** (与 106k/207k 都不同)

### 结论

**加载 `libluajit-5.1.so.2` + 3 个 Lua 模块对全进程性能无明显影响。**
差异来源是 conf 文件被多次 python 编辑污染, 非 LuaJIT 问题。

## 六、问题记录

### P1. HT 兄弟核限频 (i9-12900H + intel_pstate)

**症状**: `taskset -cp 4`(HT0) = 4.3GHz, 110k RPS; `taskset -cp 5`(HT1) = 400MHz, 50k RPS。性能差 2x。

**根因**: `intel_pstate` 在 `performance` governor 下仍将 HT 兄弟核限至最低频 (400MHz)。`scaling_cur_freq` 验证:
```
cpu4 (HT0): 4300000   (4.3GHz)
cpu5 (HT1): 400000    (400MHz!)  
```

**影响**: 所有绑核到 HT 范围的基准测试都可能跑在限频核上, 数据不可信。

**CPU 拓扑 (i9-12900H)**:

| 类型 | 物理核 | HT | 逻辑核 | 最高频率 |
|:----:|:------:|:--:|:------:|:-------:|
| P-core | Core 0-5 (6个) | HT0 / HT1 | cpu0-11 | 5.0GHz |
| E-core | Core 6-13 (8个) | 无 | cpu12-19 | 3.8GHz |

- **HT（超线程）≠ 超频**：HT 是一个物理核虚拟成两个逻辑核，频率不变；超频是提高频率
- P-core 不带 HT 的 8 个 E-core 只是频率较低的慢核，跟超频无关

**解决方案**: 
- **绑 P-core 的 HT0（偶数 CPU）**: `taskset -cp 0,2,4,6,8,10 $(pgrep Hello_robot_W0)`
  - cpu0,2,4,6,8,10 = 6 个不同 P-core 各取最快线程
- 不绑 HT1（奇数 1,3,5,7,9,11），intel_pstate 将其限频至 400MHz
- 不绑 E-core（12-19），频率低一截且无 HT
- 或在 BIOS 关闭 Hyper-Threading
- 或在 `intel_pstate=disable` 内核参数下用 `acpi-cpufreq`

| 因素 | i9-12900H (笔记本) | Xeon (服务器) |
|------|:------------------:|:--------------:|
| TDP | 45W (散热受限) | 150-280W (散热充裕) |
| intel_pstate HT 行为 | 空闲 HT 核压到 400MHz | 双 HT 核频率基本一致 |
| 混合架构 | P-core + E-core 调度复杂 | 同构全大核 |
| 典型频率 | HT0=4.3GHz, HT1=400MHz | HT0≈HT1≈3.4-4.0GHz |
| HT 绑核必要性 | 必须只绑 HT0 | 无需特殊处理 |

> 笔记本的 HT 限频是 TDP 散热限制下的 intel_pstate 行为, 至强服务器上不会出现, 绑核时无需特殊处理。

### P3. asio_uring ModuleRaw 404 (缺 MUDULE_CREATE)

**根因**: `ModuleRaw.cpp` 从创建起就缺 `MUDULE_CREATE(ModuleRaw)`，so 无 `create` 符号。
- ev: Receive Fast-Path 拦截 `/hello/raw`，不走 dlopen → **一直"正常"但掩盖了 bug**
- asio_uring: 走正常 Codec → dlopen 失败 → 404

**修复**: 加一行 `MUDULE_CREATE(ModuleRaw);`

**#67 原始诊断 (Receive Fast-Path 竞态) 为误判**: `SendToClientFast` + `SubmitRead` 竞态未被实际触发，Non-2xx 由 404 引起。
