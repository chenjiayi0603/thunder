# Thunder 管理后台重构设计（参考 Nacos）

> 设计日期：2026-07-09  |  状态: 📋 设计阶段  |  关联: #134 加权路由、#135 Python CLI
>
> **现有 admin-web 是早期拼凑产物——单文件 Python http.server + 裸 JS，功能堆叠、没有设计、不可维护。本次重构目标：达到 Nacos 的管理体验标准。**

---

## 0. 现状问题

```
deploy/admin-web/
├── server.py        ← 单文件，混杂所有逻辑（静态文件 / SO上传 / Lua管理 / etcd代理）
├── index.html        ← 无框架，裸 HTML + 内嵌 JS，难以扩展
├── plugins/          ← SO 上传目录
└── Testing/          ← 测试文件
```

| 问题 | 表现 |
|---|---|
| 无导航结构 | 所有功能挤在一个页面，靠堆砌 tab/按钮区分 |
| 无组件化 | HTML/JS/CSS 混在一起，加一个功能要改 300 行 |
| 无状态管理 | 页面数据靠全局变量，刷新全丢 |
| 交互粗糙 | 没有确认弹窗、没有加载状态、没有错误提示 |
| 后端耦合 | API 逻辑内嵌在 http.server 的 do_GET/do_POST 里 |

---

## 1. 设计目标

对标 Nacos 管理后台的核心体验：

| Nacos 做的 | Thunder 怎么做 |
|---|---|
| 服务列表卡片化（一眼看到实例数和健康状态） | 从 etcd `/thunder/registry/` 读节点，按 node_type 分组卡片展示 |
| 实例详情（IP、端口、版本、元数据） | 解析 etcd registry JSON，展示 node_version/worker_num/心跳 |
| 配置管理（在线编辑、diff 对比） | 已有的 etcd config 功能，UI 重构为专业编辑器 |
| 权重调整（拖滑块） | 等 #134 完成，滑块写 `/thunder/canary/` 权重键 |
| 操作确认（防误操作） | 每次写 etcd 前弹确认框，显示变更前后对比 |

```
│  │  10.0.0.2:16002  v1  ● 在线   权重 40                 │    │
│  │  10.0.0.3:16003  v2  ● 在线   权重 20                 │    │
│  └───────────────────────────────────────────────────────┘    │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

**交互流程**：

```
① 页面加载 → fetch /api/nodes + /api/canary-weights
     ↓
② 展示当前权重（百分比条 + 滑块位置 = 当前值）
     ↓
③ 用户拖 v2 滑块从 20% → 30%
     ↓ (实时预览，不生效)
④ 百分比条更新为 v1:70% / v2:30%，变更预览区高亮 diff
     ↓
⑤ 点 [确认变更]
     ↓
⑥ 弹确认框: "将 LOGIC 权重从 {v1:80,v2:20} 改为 {v1:70,v2:30}？"
     ↓ 确认
⑦ POST /api/canary-weights → etcd put → Manager Watch → Worker 生效
     ↓
⑧ 滑块锁定为当前值（从 etcd 回读确认）
```

**一键操作按钮**：

```
[全量 v2]    → 弹确认框 → PUT {"v1":0,"v2":100}   → 100% 流量切到 v2

[回滚]       → 弹确认框 → 自动检测上一稳定版本
                           或手动选目标版本
                           → PUT {target:100}

[恢复一致性哈希] → 弹确认框："将删除灰度配置，所有流量恢复一致性哈希路由？"
                 → DELETE /thunder/canary/LOGIC/weights
```

## 5. 交互规范

所有影响 etcd 的操作遵循同一套防误操作流程：

```
操作按钮 → 变更预览弹窗（展示 before/after diff）→ 确认 → 执行 → 结果反馈
```

| 规范 | 说明 |
|---|---|
| 加载态 | 所有 fetch 操作显示 loading spinner |
| 错误态 | API 调用失败显示 toast 通知（红色，3s 自动消失） |
| 成功态 | etcd 写入成功显示 toast 通知（绿色，3s 自动消失） |
| 确认弹窗 | 权重变更、删除配置等破坏性操作必须弹窗确认 |
| 灰度滑块 | 拖拽时实时预览百分比，不直接提交；需点 [确认] 才生效 |
| 实时刷新 | 概览页/节点页 10s 自动刷新；灰度页手动刷新 |

## 7. 技术选型

暂定方案 A（最小改动，最快落地），后期可按需升级为方案 B：

| | 方案 A（建议） | 方案 B（升级） |
|---|---|---|
| 后端 | 扩展 server.py（Python http.server → 加路由分发） | FastAPI |
| 前端 | 纯 HTML + vanilla JS（多 HTML 页面） | Vue 3 + Element Plus |
| 优点 | 零新依赖、改动最小、即改即用 | 组件化、专业 UI 库 |
| 缺点 | 无热更新、手动 DOM 操作 | 需 Node.js/npm 构建链 |
| 适合 | 1人维护、功能稳定 | 多人协作、频繁迭代 |
