# WASM 轻量沙箱 vs SO 模块 vs Lua 脚本 — 热更新方案对比

> 日期: 2026-06-10

## 背景

当前 Thunder 支持 SO 模块热更新 (#45)，需要 `GracefulRestartWorker`（进程重启）。WASM 沙箱能否实现不重启进程的热更新？

## 三种方案对比

| 维度 | SO 模块 | WASM 沙箱 | Lua 脚本 |
|------|:-------:|:---------:|:--------:|
| 执行方式 | 原生机器码 | 沙箱字节码 | 解释执行 |
| 热更新 | 进程重启 | **实例替换, 不重启进程** | **重载文件, 不重启进程** |
| 隔离性 | 弱 | 强 (沙箱) | 强 (VM) |
| 安全 | 无限制 | 受限 syscall | 受限 API |
| 性能 | **~3ns/调用** | ~30ns (AoT) | ~150ns |
| 语言 | C/C++ | Rust/C/C++/Go | Lua |
| 编译 | 需编译 | 需编译 | **不需编译** |

## 调用开销理论分析

Base: 每请求 CPU 时间 ≈ 3.1μs (3100ns)。纯函数调用开销占比:

| 场景 | SO (~3ns) | WASM (~30ns) | Lua (~50-150ns) |
|------|:---------:|:------------:|:---------------:|
| echo 类 (几乎无业务) | −0.1% | −1.0% | −1.6%~−4.6% |
| 有 JSON/PB (≈1μs 业务) | **忽略** | **<0.3%** | **<0.5%~1.5%** |
| 计算密集型 (10次调用) | −1.0% | −8.8% | −15%~−33% |

关键: 普通业务请求下三种方案差距不大, 只在 echo 类或计算密集场景才明显。

## 结论

| 需求 | 推荐 |
|------|------|
| 性能优先 | SO 模块 |
| 不重启进程 | WASM 沙箱 (建议 P0 验证) |
| 动态脚本 | **不需要 Lua**, etcd 配置 + SO 已覆盖 |

## P0 验证计划

### 目标
验证 WASM 模块可被 Thunder 加载、调用、处理请求并返回响应。

### 步骤

| # | 内容 | 预估 |
|:-:|------|:----:|
| 1 | 集成 WAMR (WebAssembly Micro Runtime): 下载源码, CMake 接入编译 | 1天 |
| 2 | 编写 WASM echo module: Rust/C 编译 .wasm, 导出 `AnyMessage()` 函数 | 1天 |
| 3 | WASM 宿主导入: Thunder 加载 .wasm, 调用 `AnyMessage`, 返回响应 | 1天 |
| 4 | 验证链路: wrk 压测 WASM echo vs SO echo, 记录 RPS/延迟差异 | 0.5天 |
| 5 | 热替换: 不重启进程, 替换 .wasm 实例, 验证请求流向新版本 | 1天 |

### 验证指标

| 指标 | 预期 |
|------|------|
| WASM echo 可达 RPS | ≥ 300k (SO 的 85%+) |
| 热替换无中断 | 替换期间 0 请求失败 |
| 内存增长 | 每 WASM 实例 ≤ 512KB |

### 风险

- WAMR 与 Thunder 的 CMake 构建系统兼容性
- WASM 导入函数 (SendToClientFast 等) 的绑定复杂度
